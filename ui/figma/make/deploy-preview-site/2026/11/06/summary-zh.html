「背景」 MoE 通过路由器把每个 token 分发给部分专家，从而在参数量增大的同时控制单次计算量，但路由、负载均衡和分布式并行配置比稠密模型复杂得多。Megatron-LM 是常用的分布式训练框架，其 MoE 相关参数分散且不易理解，这份手册正是针对这一门槛编写的操作指南。

OpenSSH 10.6p2 修复 Alpine 长密码认证绕过漏洞 ⭐️ 8.0/10

OpenSSH 于 11 月 5 日发布 10.6p2 版本，紧急修复一个在 Alpine Linux 上可用 257 至 1024 字节长密码绕过 SSH 认证的漏洞。攻击者需具备服务器网络访问权和目标账户名，即可借此登录未设置密码的密钥账户。Alpine 已为 3.16 以后版本发布修复包，暂无法升级者可设置 PasswordAuthentication no 关闭密码登录。目前尚无该漏洞的利用报告。

telegram · zaihuapd · 11月5日 16:44

「背景」 该漏洞编号为 CVE-2026-123158，由研究者 Ozgun Kultekin 发现，OpenSSH 于 2026 年 11 月 5 日发布 10.6p2 紧急版本予以封堵，Alpine 同日将修复回溯移植到 3.16 及之后的各分支。Alpine 的安全公告提醒，仅升级软件包不会替换正在运行的守护进程，升级后必须重启 sshd 才能生效。

「影响与处置」 运行 Alpine Linux 3.16 及以后版本并启用 SSH 密码认证的服务器受影响，应尽快安装 Alpine 发布的修复包；若无法立即升级，可先设置 PasswordAuthentication no 关闭密码登录作为临时缓解。

Claude Code 被指将用户邮箱发送给网站 ⭐️ 7.0/10

GitHub 上出现一个关于 Claude Code 将用户邮箱地址发送给所访问网站的 issue，并在 Hacker News 引发讨论。评论者 varenc 指出，许多报告的情形与 SEC API 有关，并称 SEC API 文档要求把邮箱写入 User-Agent，否则请求会被拒绝，因此部分泄露可能源于第三方 API 的要求，而非 Claude Code 主动外发。目前该行为的具体范围、触发条件和 Anthropic 的官方说明均未在材料中给出，相关说法仍属社区观察与推测。

hackernews · motoroco · 11月5日 22:17 · 社区讨论

「背景」 该讨论涉及美国证券交易委员会（SEC）的公开数据接口 data.sec.gov：它不使用 API 密钥，但要求请求方在 User-Agent 头中提供有效标识并遵守速率限制，否则请求会被拒绝。评论者据此推测，部分“邮箱被发送”的情况可能源于满足这类第三方接口的请求要求，而非 Claude Code 主动外泄。

「影响与应对」 对使用 Claude Code 访问外部 API 的开发者而言，需要留意请求头中可能携带账号邮箱等身份信息，尤其是 SEC API 这类明确要求 User-Agent 含邮箱的服务；在涉及隐私敏感项目时，应检查网络请求日志并考虑限制工具的网络访问。

「社区讨论」 评论者 grey-area 主张 Claude 不应访问用户资料或沙箱外文件，也不应在没有完整请求日志的情况下联网，认为实例应被更严格地沙箱化。另有评论者 mk89 称切换到 Claude 后工作邮箱垃圾邮件明显增多，但这只是个人经历，无法据此证明与 Claude Code 存在因果关系。

trainlint：用静态检查捕捉不会报错的 ML 训练错误 ⭐️ 7.0/10

作者发布了一个基于 Python AST 的小型静态检查工具 trainlint，用于发现十四类不会抛出异常的机器学习训练与评估错误，包括先在全量数据上做特征选择再交叉验证造成的数据泄漏、训练时忘记调用 eval()、在 CrossEntropyLoss 前先做 softmax、backward 与 step 之间调用 zero_grad、把 y_true 与 y_pred 写反等。作者用 5000 个随机特征和随机标签演示泄漏：在全量数据上选前 20 个特征再做 5 折交叉验证得到 85% 准确率（20 个随机种子平均 87.7%），而把选择放进 Pipeline 后为 48%（平均 50.0%），说明差距全部来自泄漏。该工具只按名称匹配、一次读取一个文件，仅支持 PyTorch 和 scikit-learn，不需要数据、模型或 GPU。作者在 pytorch/examples 固定提交上人工核对得到 22 条报告，其中 20 条为真实问题、2 条正确但无害，并明确表示没有召回率数据，测试脚本与规则是一起写的。

reddit · r/MachineLearning · /u/Possible-Active-1903 · 11月5日 16:54

「背景」 这类“静默错误”不会让程序崩溃，却会悄悄抬高验证指标或让训练失效，例如在划分数据集之前用全量统计量做预处理，或训练循环中始终没有切换到评估模式。静态分析通过解析源码结构而非运行程序来发现模式，因此可以在没有数据和算力的情况下提前报警，但代价是依赖命名约定，遇到不常见的变量名或拆分方式容易误判。

「影响」 对使用 PyTorch 或 scikit-learn 的开发者，这个工具可以在跑实验前提示泄漏和训练循环配置问题，但作者只在一个教程仓库上做过人工核对，且没有召回率数据，因此更适合作为辅助检查而非正确性保证；代码中若用非常规命名表示训练/验证划分，可能产生漏报或误报。

数据库本质上是全局变量的存储 ⭐️ 7.0/10

rss · Sean Goedecke · 11月6日 00:00

「背景」 编程界普遍告诫“全局变量是坏的”，但许多优雅的系统却依赖数据库。作者指出，数据库中的行或记录在定义上就是全局变量：程序任何部分都能读写它们，因此同样会带来隐式传参和跨模块耦合的问题。那么，为什么数据库没有让应用架构变得一团糟？

「方案」 作者逐一检验了五种解释。第一，也许数据库应用确实很乱，但作者认为它们并没有那么糟，而且同一代码库中人们仍会刻意避免普通全局变量。第二，ACID 保证并非关键，因为全局变量的问题不在于状态不同步，而在于它存在本身；若加个互斥锁就能接受，那论证就站不住脚。第三，数据库更显式：查询需要传入连接对象并调用查询函数，扫描代码时一眼可见，这确实缓解了隐式耦合。第四，数据库更不灵活，作者只认同一半：在无类型语言中，全局变量可被重新赋值为任意类型，确实更可怕，但该建议同样适用于有类型语言，所以不是根本原因。第五，我们熟悉数据库的使用规范：读列时检查类型，不会用数据库在循环里计数或存配置文件名，这些惯例减少了损害。作者最终认为第三和第五点最有说服力，并强调这些原因是偶然的、非固有的：一个有全局变量使用约定的代码库也能满足同样条件。

「启示」 作者的核心论点是：“避免全局变量”和“用数据库存状态”这两条常见教条部分不一致，多数软件设计知识仍只是一堆松散的经验法则。因此，面对以“最佳实践”为由却给不出具体理由的工程师，我们应保持怀疑，哪怕是在“全局变量不好”这样看似显然的问题上。
